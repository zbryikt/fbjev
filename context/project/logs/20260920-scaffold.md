# 20260920 - extension 框架落地

依 `context/project/initiative/index.md` 建出 MV3 extension 的完整骨架，判讀管線端到端可跑。


## 做了什麼

 - `web/src/raw/manifest.json` — MV3，content script 掛在 `https://*.facebook.com/*`
 - `web/src/ls/content.ls` — MutationObserver 找新貼文，IntersectionObserver 過濾到視窗內才送判讀
 - `web/src/ls/background.ls` — service worker，持有 key、指紋快取、併發上限 3 的佇列
 - `web/src/ls/lib/` — `log` `config` `post` `analyzer` `jev` `badge` 六支共用模組
 - `web/src/ls/popup.ls` + `web/src/pug/popup.pug` — 設定與統計面板
 - `package.json` 補上 `build` / `start`；`.gitignore` 排除 `web/static` 等建置產物


## 幾個決定

判讀一律走 service worker，不在 content script 直接打 API。理由有三：API key 不進頁面、
跨分頁共用同一份快取與佇列、fetch 不受 FB 頁面的 CSP 限制。

保留一個本地 heuristic 的 `mock` provider。它讓整條管線在沒有 API key 時照樣跑得動，
改 FB 選擇器或 badge 樣式時不必打 API；判準本身刻意粗糙，真正的判讀是模型的事。

去重用「作者 + 內文前 400 字」的 djb2 指紋，不用 DOM 節點或貼文 URL。FB 無限捲動會把
同一則貼文重新掛載，節點識別留不住；而不少貼文根本抓不到 permalink。


## typesafe.ai 文件查證結果

文件是公開的，`https://docs.typesafe.ai/llms.txt` 有完整索引。

    POST https://api.typesafe.ai/v1/systemone
    Authorization: Bearer <API_KEY>

`noul` 問題型別剛好對上需求：一題一個 yes/no 命題，直接回 0 到 1 的機率，
不必要求模型吐 JSON 再解析，五個面向一次請求問完（約 800 input tokens）。回應形如
`{model, answers: {<id>: {type, noul}}, usage}`。model 用別名 `jev-latest`，
目前指向 `jev-1.13.0`。429 與 529 是文件明列的暫時狀態，client 退避重試一次。

    Club Med ( 贊助 )        AI 58  廣告 97  網軍 17  仇恨 1  小白 6    收合 714px -> 72px
    技術社團的梗圖貼文         AI 28  廣告 10  網軍 14  仇恨 3  小白 15   不收合

那則廣告的「贊助」標示我們抓不到, 97 分純粹是模型讀內文判出來的, 反過來支持了
「不傳恆為 false 的 sponsored 旗標」這個決定。


## 途中修掉的四個問題

第一版的選擇器整組沒中。主 feed 的貼文單元不是 `[role="article"]` ( 那是留言與其他版型 ),
而是虛擬列表的 `div[data-virtualized]`, 內部區塊掛 `data-ad-rendering-role`。頁面上僅有的
四個 `role="article"` 全是載入骨架。

標記時機太早。骨架階段就把元素標成已處理, 等 FB 把內容填進來時已經被永久跳過。改成掃描
只掛觀察、抽到內容才標記, 而且標記寫的是內容指紋不是處理旗標 —— `data-virtualized` 的意思
就是節點會被回收裝下一則, 只記旗標會讓回收後那則永遠漏掉。

manifest 的 content_scripts 漏列 `analyzer.js`, `badge.render` 取 `analyzer.dimensions` 時炸掉。
判讀其實成功了, 死在渲染最後一步。

擴充功能重載後, 舊分頁的 content script 變成孤兒, `chrome.runtime.sendMessage` 會同步 throw
而不是回 rejected promise, `.catch` 接不到, 於是每則進入視窗的貼文都丟一個 uncaught error,
標記永遠停在 pending。現在 `watcher.send` 用 try/catch 包住, 失聯就停掉觀察並要求重整分頁。


## 一個測試環境的坑

Claude in Chrome 控制的分頁是 `document.visibilityState: "hidden"`, 而 IntersectionObserver
在分頁不可見時不會觸發 —— 這是瀏覽器的正常行為, 也正是這個 extension 該有的行為 ( 沒人在看
就別花 API 錢 ), 但會讓自動化測試看起來像「功能壞了」。把分頁 focus 交出去之後整條鏈立刻通。
下次自動化測 IO 相關的東西要先確認 visibility。
